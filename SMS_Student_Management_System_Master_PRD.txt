============================================================
1. PROJECT OVERVIEW
============================================================

Build a production-ready Scholarship-focused Student Management System named:

SMS — Student Management System

Technology constraints:
- Frontend: HTML5, CSS3, Vanilla JavaScript only.
- Backend: Supabase.
- Database: PostgreSQL through Supabase.
- Authentication: Supabase Auth.
- No React.
- No Vue.
- No Angular.
- No TypeScript.
- No unnecessary framework.
- Use a small number of reliable CDN libraries only when genuinely needed.
- Charts may use a lightweight chart library such as Chart.js via CDN.
- The application must work on Android phones, iPhones, tablets, laptops and desktop screens.
- The UI must never create horizontal overflow on normal screen sizes.
- The code must be modular, readable, maintainable and free of duplicate logic.

The system is primarily an ADMIN scholarship management application.

There is NO normal student login.

Students receive a secure shareable link/token that lets them view their own scholarship/application information in a read-only public/student view.

IMPORTANT:
Do not expose Supabase service-role keys in frontend code.
Only use the Supabase anon/public key in the browser.
All sensitive database access must be protected by authentication and Row Level Security (RLS).

============================================================
2. CORE BUSINESS PURPOSE
============================================================

The administrator should be able to:

1. Create and manage many scholarships.
2. Store scholarship name, description, eligibility, required documents, deadline, benefit amount and other useful information.
3. Define scholarship-specific application statuses/options.
4. Create and manage student records.
5. Select a scholarship for a student.
6. Find suitable scholarships using a smart eligibility filter.
7. Manually assign any scholarship when needed.
8. Record application ID, portal/application URL, username/user ID and password/credential information if required.
9. Record application date.
10. Track current application status.
11. Record scholarship benefit/amount.
12. Configure commission percentage.
13. Automatically calculate commission amount.
14. Allow entering commission amount/percentage with automatic reverse calculation where appropriate.
15. Record payments.
16. Track payment status and payment history.
17. Create a shareable student link.
18. Allow the student to view relevant information through that link without normal login.
19. Maintain an Important Links section.
20. Display dashboard statistics.
21. Display a scholarship/application status pie chart.
22. Search, filter, sort and manage records easily.
23. Keep the interface simple rather than over-complicated.

16. SMART SCHOLARSHIP FILTER
============================================================

Create a simple smart eligibility engine.

Purpose:
When admin opens a student's profile and clicks "Find Eligible Scholarships", the system should compare student information against scholarship eligibility fields.

Matching examples:
- Course matches
- Education level matches
- State matches
- Income is within limit
- Percentage meets minimum
- Age meets range
- Category matches
- Other configured criteria

Results should show:

"Likely Eligible"
"Possibly Eligible"
"Not Eligible"

Each result should show WHY.

Example:
Scholarship A
Likely Eligible
✓ Course matches
✓ Income within limit
✓ Minimum percentage met
✓ State eligible

Scholarship B
Possibly Eligible
✓ Course matches
? Category information missing
✓ Income within limit

The engine must not claim legal/official eligibility. Label it as a screening/matching tool.

Buttons:
- Assign Scholarship
- View Details
- Ignore
- Apply Manually

IMPORTANT:
Admin must always be able to manually assign a scholarship even if the smart filter does not recommend it.

19. COMMISSION SYSTEM
============================================================

The admin can define commission percentage.

Example:
Scholarship benefit = ₹12,000
Commission = 40%

Automatic calculation:
Commission amount = ₹12,000 × 40 / 100
Commission amount = ₹4,800

Net amount can optionally be shown:
₹12,000 − ₹4,800 = ₹7,200

Support two input modes:

MODE A:
Admin enters benefit amount + commission percentage.
System calculates commission amount automatically.

MODE B:
Admin enters benefit amount + commission amount.
System calculates commission percentage automatically.

If both percentage and amount are edited:
- Use an explicit calculation mode selector.
- Never silently overwrite user input.
- Show which value is being calculated.

Validation:
- Commission percentage: 0–100.
- Amount cannot be negative.
- Currency-safe calculation.
- Store monetary values as numeric/decimal, not floating-point text.

Display:
- Benefit Amount
- Commission %
- Commission Amount
- Net Amount

22. SHAREABLE STUDENT LINK
============================================================

Students do not receive normal login credentials.

Admin clicks:
"Create Share Link"

System creates a secure random token.

Example conceptual URL:
https://your-domain.com/shared.html?token=RANDOM_SECURE_TOKEN

Requirements:
- Token must be cryptographically random.
- Token must not contain student ID or personal information.
- Token should have an expiration option.
- Admin can revoke a token.
- Admin can generate a new token.
- Old token can be invalidated when requested.
- Do not use sequential IDs.
- Do not put database IDs directly into the public URL when avoidable.

Shared page should display only approved/safe information.

Shared student view:
- Student name
- Student ID if admin chooses to expose it
- Academic information selected for sharing
- Scholarship name
- Scholarship provider
- Application ID if enabled
- Application date
- Current status
- Benefit amount if enabled

- Important links
- Notes that are marked shareable

NEVER show:
- Admin login details
- Supabase keys
- Internal database IDs
- Private admin notes
- Portal passwords

- RLS/security metadata

Provide:

27. RLS / SECURITY
============================================================

Enable Row Level Security on all application tables.

Admin access:
- authenticated users with role=admin can read/write admin data.

Do not rely only on frontend route protection.

Use PostgreSQL RLS policies.

Public shared view:
- Do NOT simply create a policy allowing anonymous users to SELECT the entire students table.
- Public access should go through a narrow, secure mechanism.
- Prefer a Supabase Edge Function that:
  1. Receives the share token.
  2. Hashes the token.
  3. Checks validity and expiration.
  4. Checks revoked_at.
  5. Returns only explicitly shareable fields.
  6. Never returns credentials/passwords.
  7. Does not expose arbitrary student records.

The frontend must never contain a service-role key.

43. SHARE LINK SECURITY FLOW
============================================================

Recommended flow:

Admin:
1. Click Create Share Link.
2. Choose expiration.
3. Choose shareable fields.
4. Backend generates secure random token.
5. Backend stores token hash.
6. UI receives the one-time/raw token only for constructing the link.
7. Admin copies link.

Student:
1. Opens shared URL.
2. Frontend sends token to secure Edge Function.
3. Function hashes token.
4. Looks up valid token.
5. Checks expiry/revocation.
6. Fetches safe fields.
7. Returns only safe data.
8. Updates last_accessed_at.

Never:
- Query students directly from anonymous frontend.
- Use predictable tokens.
- Return all columns.
- Return credentials.
